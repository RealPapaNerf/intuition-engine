# Intuition Engine

A game framework for growing intuition — the ability to predict an
answer before computing it, and to smell a wrong answer when a person,
a textbook, or an AI hands you one.

First track: engineering (see `docs/intuitive-engineers-brief.md`).
Second track, planned: communication and negotiation
(`docs/intuitive-negotiators-brief.md`). Candidate tracks: comedy, and
anything else where intuition is trainable by predict-test-see-why.

## The bet

It used to be that scenarios were the expensive part of educational
software, so you built one scenario and marched every kid through it.
That's inverted now: **scenarios are cheap; the engine and the learning
philosophy are the product.** With an AI coach, the costume around a
lesson can be generated per kid — but only if the things that must stay
honest are separated from the things that are allowed to be generated.

Three layers are authored, versioned, and fixed:

1. **Honest primitives.** Per domain, a small simulation whose rules
   are real: tension-only links, compression struts, elastomers,
   gravity, equilibrium (engineering); hidden-state characters with
   consistent trust rules (negotiation). The AI may dress these; it may
   never invent physics. A kid's intuition is only worth building if
   it's calibrated against reality.
2. **The loop and its scoring.** Predict before you test, every time;
   calibration as the prestige stat; the superintendent rule (full
   points for any honest solve, a bonus for doing it like an engineer,
   a human-confirmed jackpot for a way nobody has tried); the
   question-only coach and the deliberately fallible Consultant.
3. **The concept ladders.** What spirals and in what order: tension
   before leverage before load paths; feel it → measure it → model it.
   This is the syllabus, and it's authored because pedagogy has
   dependencies that theming doesn't.

One layer is generated, per kid, and disposable:

4. **The skin.** Frogs, ants, spiders and termites are the *reference
   skin* — one person's interests, used to prove the games. A kid who
   loves excavators, dragons, or ballet gets the same primitive wearing
   their world, generated by the AI coach inside the authored rules. A
   level is an *archetype* ("span a gap using tension-only and
   compression elements, under budget, holding X") plus a skin; the
   archetype is what gets scored, compared, and archived in the Museum
   of Solutions, so personalization never breaks comparability between
   kids or the teacher's ability to judge work.

## What's here

| Path | What it is |
|---|---|
| `docs/` | The track briefs — the plans of record |
| `engine/` | The shared 2D node-and-member physics engine (plain ES modules, no dependencies): springs with tension/compression limits, tension-only materials, dynamic relaxation for statics, breakage, and member-shedding topology optimization |
| `test/` | Hand-calculation validation (`node --test`): spring extension, two-bar truss forces, tension-only slack, breakage, shedding |
| `demo/` | The first playable: an ant bridge, a frog, and the lazy-colony shed. Open `demo/index.html` in a browser — no build step |

## Running it

```bash
npm test              # validates the engine against hand calculations
xdg-open demo/index.html   # or just open it in any browser
```
